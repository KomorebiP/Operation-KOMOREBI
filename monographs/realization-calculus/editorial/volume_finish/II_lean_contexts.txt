3 Reading the inherited formal walkthrough
The mathematical text develops the mathematical theory and its written proofs. The visual guide pro-
vides finite models for its identities, precision statements, and boundaries. This guide explains how to
read and use the preserved Lean component: the types accepted by each theorem, the objects actually
constructed, the obligations supplied by a caller, and the evidence attached to the source. These three
companions have complementary roles.
This walkthrough describes the foundational 25-row formal contract. The chapter-wide correspon-
dence and its boundaries are recorded in Section 1. The foundational source is preserved at source/c
anonical_v1.2.1/formalization/lean/. The versioned path identifies that exact archived component.
The mathematical text incorporates a broader written development. Its ordinary proofs of lattice gluing,
necessary precision delay, convergence in an inverse limit, general DVR arithmetic, holomorphic and
exponential defects, and multilevel identities are not converted into Lean proofs by appearing beside
formally mapped results.
The fixed formal contract contains 25 rows: 21 numbered canonical statements, one Smith phase
identity, and three mathematical algorithm specifications. The appendix crosswalk identifies their lo-
cations in the integrated traditional edition. Throughout this guide, “row” means a row of the canonical
formal map, never a count of every theorem in the mathematical text.

A name count is not a measure of mathematical depth. A short wrapper can collect several substantial
conclusions. A large structure can expose a difficult hypothesis without constructing its witness. The
useful unit is a complete type together with its proof, its dependencies, and an accurate comparison
with the prose statement.
3.1 Three useful reading routes
For a first reading, follow Sections 4–12: exact coordinates lead to weighted transfer, then arithmetic
and typed defects. For a coverage review, use the crosswalk to the mathematical text in Appendix A,
read the corresponding row in Section 15, and inspect its source type. For a reproduction attempt, read
Section 13 before running any build command. The source checksum check and the compiler audit
establish different things.
The main walkthroughs use exact source excerpts, with explanatory equations outside the listings.
Names are case sensitive. PowerSeries, Polynomial, LinearMap, and ContinuousLinearMap are different
types. Similar notation is not a license to replace one with another in a theorem application.

13.3 A minimal session for source inspection
After a successful build, create a scratch Lean file beside the project’s aggregate import. The following
inspection commands ask Lean to display two representative declarations and the axiom dependencies
of the automatic rationality result.
import KomorebiVerification.PaperII
#check Komorebi.PaperII.NestedRefinement.coordinateRefinementEquiv
#check Komorebi.PaperII.SmithDyadic.smithZMod_global_conditional_count
#print axioms
Komorebi.PaperII.TransferZeta.PositiveWeightedMultigraph.finite_graph_pathZeta_rationality
↪
Run it with lake env lean YourInspection.lean. These are suggested inspection commands, not
a new executed transcript. Use #print or editor hover to inspect elaborated types, including inferred
section parameters and typeclass assumptions. The printed source excerpt alone may omit surrounding
binders. The full declaration type is decisive.
When applying a theorem, first fix the intended scalar type and domain/codomain. Then assemble
the structural object and prove its fields. For a weighted inverse, this means the filtration, map 𝑞, pre-
cision certificate, diagonal inverse, and edge expansion. For a finite graph, it means finite vertex/edge
types, endpoint maps, and positive weights. For a Smith system, it means a diagonal weight function
and modular target. This preparation makes failures informative: a missing instance differs from a
missing mathematical witness.

C Source excerpts and reproduction inventory
Every printed Lean listing comes from an exact UTF-8 excerpt in excerpts/*.lean.txt. The adjacent
*.render.txt file escapes TeX control characters and substitutes a math font glyph where the code font
lacks one. It preserves token order. Exact source text, not the display fallback, is the object to copy into
an editor. Excerpts retain their surrounding source context only when that context is printed. They are
not standalone Lean files. generated/excerpts.json records each source path, inclusive source line
range, the SHA-256 digests of each full source file, exact excerpt, and display file. generated/theore
m_map.json contains all 25 rows with fully qualified targets, classifications, scopes, boundaries, and
lexical source locations. generated/mapped_source_index.json provides an alphabetical target index.
generated/static_identity_audit.json records all manifest comparisons and the optional baseline
comparison performed for this edition.
build_guide_data.py uses only the Python standard library. It generates the map, import table,
pins, excerpts, and current static audit without invoking Lean. build_guide.sh calls that generator and
runs XeLaTeX four times. The monograph build uses system-installed P052, Nimbus Sans, DejaVu Sans
Mono, and Latin Modern Math fonts with recorded dependency hashes. The required LaTeX packages
are listed in the preamble. The independent PDF check script uses PyMuPDF and Pillow for page
rendering and contact sheets.
The foundational source remains preserved. The broader constructions live in formal/current/
and are indexed by the chapter-wide correspondence. Editing this guide cannot by itself repair or
strengthen a Lean theorem. A mathematical change to the formal component requires a separate source
change, a new compile, an updated map when appropriate, and new execution evidence.
