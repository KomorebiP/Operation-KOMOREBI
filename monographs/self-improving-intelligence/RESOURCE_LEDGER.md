# Resource ledger — first consolidated edition

## One accounting boundary

Each comparison must refer to the same permitted problem, input access, installed programs, stopping rule, and acceptance standard. Baseline and revised workflows can share setup only when they actually share it. A model-record read is one explicit table lookup, not one CPU instruction. Literal tree records are not bytes. Retained storage, peak memory, and cumulative work require different combination rules.

## Phases that must remain visible

| Phase | Actual accounting in this edition | Boundary |
|---|---|---|
| Supplied semantics and models | Explicit finite tables and arithmetic definitions | Generating a mathematical table is not learning a physical model. Calibration and theorem discovery are not measured. |
| Common input validation | Separate shape/scope table scans | Not deducted from one competitor while charged to the other. |
| Candidate construction | AST counts, literal node occurrences, feature lookup and search traces | These are distinct units, not a claim to count every Python operation. |
| Equation acquisition | 1,215 probe evaluations, 3,519 probe interpreter visits, 1,068 equation proposals | Finite equality of outputs only proposes a rule. |
| Proof admission | 336 admitted equations and 584 successful replayed axiom steps | Failed search and bookkeeping are separate overheads. The checker is not a proof-assistant kernel. |
| Installed equation library | 69,518 bytes in the specified compact serialization | Not a lower bound on information content or Python memory consumption. |
| Search-representation preparation | 19,440 normalization visits, 518,140 schema matches, 4,798 successful rewrites | Must be amortized rather than charged only after a favorable target is known. |
| Downstream rule acquisition | Original capacity rule: 1,898 -> 1,376 interpreter visits; ten-target batch: 196,384 -> 85,162 | Same exact proposal and counterexample trace under supplied teacher assumptions; preparation is extra. |
| Diagnostic compilation | Model reads, repair-set tests, additions and comparisons separately | Full scan and streaming use identical query/row order and verify the returned witness. |
| Online controller | Worst-case execution and full stored tree | Full storage includes branches never visited in an individual episode. |
| Revision management | Direct bindings, checker replays and proof/witness records | The manager is not free. Its demonstration does not provide a total processor-time speedup claim. |
| Release validation | Recorded commands, wall limits and execution receipts | Development/auditing expense, not online repair work. |

The source programs and full execution receipts disclose additional phase counters. Omitted physical costs, implementation overheads, and human construction costs are not silently assigned zero.

## Actual weighted-search comparison

The 32-case paired-repair model requires sixteen repair classes. Both search methods return the same controller with five online units and 31 stored records.

| Search event | Full scan | Streaming | Old minus new |
|---|---:|---:|---:|
| Model-record reads | 4,416 | 2,864 | 1,552 |
| Rational additions | 4,544 | 2,992 | 1,552 |
| Capacity comparisons | 1,073 | 2,941 | -1,868 |

Both also pay 1,152 scope reads and 256 witness reads, so these common terms cancel in this isolated search difference. Weight construction itself records 512 membership checks and 32 load updates; its scope replay is also recorded. These common/preparatory costs remain part of a complete assessment.

With prices in the displayed order, (1,1,1) gives 1,236 units saved, (1,0,1) gives -316, and (0,0,1) gives -1,868. The controller remains correct under each cost interpretation. The paper does not select a favorable price vector and call it a measured runtime.

For an explicitly hypothetical additional setup of 2,000 comparison units, equal prices give -764 after one use and +472 after two. This is an illustrative ledger, not the measured acquisition cost of the entire system.

## Formal criterion

For per-workload-class event savings s_i, use counts n_i, and additional setup vector K, define Delta(n) = sum_i n_i s_i - K. Price-independent nonnegative saving over all nonnegative prices requires every coordinate of Delta(n) to be nonnegative. For a specified convex hull of finitely many price vectors, the worst price is attained at one of the listed vertices.

Storage-duration pricing or peak-memory limits require a separately stated model. The additive theorem does not silently transform those resources into cumulative event counts.
