\section{Reproduction, audit, and evidence handling}
\subsection{The exact environment}
The canonical release is v1.0.0, dated 5 September 2026. Its toolchain file specifies \code{leanprover/lean4:v4.34.0-rc2}. The recorded compiler commit is \code{6a10ac8c22beadecabdbb0919c2b50214762f91d}. Mathlib is pinned at \code{aeb72f1e9981b6d35b426b16dca7759be3e7ba06}. The complete nine-package revision table is printed in the dependency appendix and preserved in \code{lake-manifest.json}.

The project has \code{autoImplicit = false} and \code{relaxedAutoImplicit = false}. Warnings are fatal in the release build. The aggregate import integrates the development, while the explicit kernel audit checks the mapped declarations and the namespace. Build caches are excluded from the release source.

\subsection{What the saved kernel transcript establishes}
The saved transcript contains one axiom record for each of the 1,164 mapped targets and ends with the namespace audit's pass line. The guide generator compares the target sets in four places: the theorem map, the declaration-kind contract, the audit source's explicit directives, and the transcript. It also checks that every recorded axiom belongs to the three-item permitted set.

This reconciliation proves consistency of the preserved evidence files with the preserved source identities. It does not repeat elaboration, type checking, or a live environment traversal. The namespace totals of 2,234 declarations and 1,999 theorem declarations are inherited results, not counts newly obtained from a running Lean process. A lexical source parser cannot substitute for elaborated declaration types or compiler-generated declarations.

\subsection{Current checks for this guide}
The generator validates every one of the 119 Lean source files against the canonical SHA-256 manifest. It resolves the 1,164 target names to source declarations and checks the theorem-versus-construction split against the explicit contract. It emits the complete row catalog, 68-result ledger, direct-import inventory, exact pins, and source-excerpt manifest.

The source policy scan excludes comments and string literals before checking for forbidden proof placeholders and unsafe shortcuts. The kernel-audit file is treated separately because its exclusion logic necessarily names prohibited axioms. This is a source-hygiene check. It does not establish that elaboration succeeds.

No new Lean build was available for this companion edition. The 43 declarations in \code{SemanticChecks.lean} remain source-level and inherited execution evidence here. They are not relabeled as 43 newly executed tests. The companion edition changes explanatory material and navigation, not the canonical Lean files.

\subsection{Replay the original release gate}
Use a disposable copy of the canonical \code{PRSC_IV} directory with the pinned Lean toolchain and dependencies available. The documented release gate requires Lean and checksums; it is not an offline-only integrity shortcut.
\begin{Verbatim}[fontsize=\small,breaklines=true,breakanywhere=true]
bash VERIFY.sh --release
\end{Verbatim}
If the original release archive is available, its exact archive-entry checks can be included:
\begin{Verbatim}[fontsize=\small,breaklines=true,breakanywhere=true]
bash VERIFY.sh --release --archive /path/to/PRSC_IV_v1.0.0.zip
\end{Verbatim}
The new three-companion edition archive is not the original canonical release ZIP. Do not pass it to a gate that expects the original release's exact entry set.

The gate also accepts a validated external dependency cache:
\begin{Verbatim}[fontsize=\small,breaklines=true,breakanywhere=true]
bash VERIFY.sh --release --lean-packages-cache /path/to/packages
\end{Verbatim}
The cache must match the pinned package revisions. The release checker requires a clean project without a preexisting local build cache. It creates and cleans its local attachment under its own rules. A fresh extracted copy is the clearest way to avoid mixing source verification with prior build state.

For a focused manual inspection from \code{formalization/lean}, the relevant commands include:
\begin{Verbatim}[fontsize=\small,breaklines=true,breakanywhere=true]
lake --wfail build
lake env lean -E warning KomorebiPaperIV/KernelAudit.lean
\end{Verbatim}
These are replay instructions, not commands claimed to have run in this companion edition. The full release gate additionally checks exact kinds and manuscript associations, source policy, document reconstruction, checksums, and archive properties when requested.

\subsection{Rebuild this guide without running Lean}
The supplied \code{build.py} compiles the existing guide with four XeLaTeX passes. It does not regenerate its data, install packages, invoke Lean, or modify the canonical source. Run it from the guide directory:
\begin{Verbatim}[fontsize=\small,breaklines=true,breakanywhere=true]
python3 build.py
\end{Verbatim}
The optional static-data generator is separate. Its defaults fit the edition's packaged folder layout, and its paths can be overridden:
\begin{Verbatim}[fontsize=\small,breaklines=true,breakanywhere=true]
python3 build_guide_data.py \
  --source /path/to/PRSC_IV \
  --traditional /path/to/editable/traditional
python3 build.py
\end{Verbatim}
It writes generated navigation and provenance inside the guide directory. The code excerpts have both untouched UTF-8 text and display-escaped copies. Display escaping preserves the source characters while allowing the chosen fonts and verbatim environment to render Lean notation. The raw excerpts are the authoritative source intervals.

\subsection{Failure modes worth recognizing}
A dependency revision mismatch means the attempted replay is not the pinned release environment. A saved transcript whose target set differs from the contract is incomplete evidence even if its final line says pass. A declaration that is present lexically but fails to elaborate has not passed a new formal run. A PDF that builds successfully says nothing by itself about the Lean proofs.

The inherited computational audit also reports that an older strengthened numerical suite accepted mutations to a projector identity and a zero-counting constant. Its reported pass totals therefore cannot certify theorems. The canonical formal contract and kernel evidence should not be replaced by those historical finite-test totals. Finite checks can still detect selected regressions, but their sensitivity and scope must be stated.

\subsection{How to inspect one result end to end}
Choose a manuscript record in the next ledger. Read all of its map rows, including later rows that close analytic clauses. Follow each exact declaration name to its source location. Inspect the surrounding variables, typeclass instances, definitions, and imported lemmas. Check the target's kind in the contract and its axiom record in the saved transcript. If a new formal run is needed, use the pinned environment and retain its complete output separately from inherited evidence.

For example, result 4.5 joins row 27's factorial/Pochhammer formal identity with row 150's literal parameter multiset, Gamma normalization, and actual convergent hypergeometric summation. Reviewing only row 27 would miss completed analytic coverage. Reviewing only the final identity would miss the coefficient normalization on which it depends. The contract is designed to make both routes visible.
