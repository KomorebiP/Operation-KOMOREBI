Edition statement

This volume presents the machine representation of Paper I as a mathematical object that can be
inspected, queried, and executed. It accompanies the traditional paper and the Lean guide. The
canonical machine object remains the JSON entrypoint and its versioned payload. The PDF is the
readable specification and catalog of that object.
The editorial edition is final for this release. This means its terminology, package paths, runtime
description, examples, and record catalog have been reconciled with the v1.0.1 interface. It does
not mean every record has a formal proof certificate. The release contains 108 records, including
definitions and boundaries, and 69 source proof bodies. Twenty records have explicit typed
signatures. Eight records have mappings to the attached historical Lean tranche, with differing
degrees of source agreement.
The traditional final edition integrates the expanded 108-record core with worked models and visual
material from the corrected traditional lineage. The machine source is the expanded core with two
explicit nonzero-packet hypotheses added after the scoped audit. Its new SHA-256 digest identifies
this corrected core. The original v1.0.0 payload is preserved separately as provenance. Added
traditional examples are not silently inserted into the KIR. Stable identifiers join the core across
the companions. A shared identifier alone is not a proof of statement equivalence.
The current documented release gate, exact finite fixture suite, and narrow zero-packet regression
were replayed successfully for this edition. No fresh Lean compilation is claimed by this companion
build. The separate Lean guide records its own formal verification scope.
How to use this volume. Read Sections 1–3 for mathematical and evidence semantics. Sections
4–6 give the executable contracts and an exact worked example. Section 7 describes release
reproduction. Appendix A reproduces every canonical source statement and every attached proof
body, with source locators and machine metadata. Later appendices give signatures, action coverage,
operation vocabulary, and the historical Lean map.

1 The mathematical object behind the interface

1.1 Operator systems, generated hulls, and seed rank

A seed problem consists of an acting algebra, a module, and a family of seed vectors. The algebra
must be fixed before the generation question is asked. For a unital algebra A acting on a module
M and a finite seed family S = {s1 , . . . , sr }, the algebraic generated hull is
                                                          r
                                                          X
                                           HullA (S) =          Asj .
                                                          j=1

A one-seed system is cyclic. Seed rank measures the minimum cardinality of a generating family,
under the regime declared in the source. Enlarging the acting algebra changes the question.
Replacing algebraic span by a closure changes it again. The machine record therefore keeps the
acting regime and hypotheses beside the statement.
Paper I begins with typed operator grammars and their realizations, then passes through free
presentations, generator number, packet coordinates, block algebras, transfer graphs, and realization.
The resulting record graph covers the whole expanded foundation. It is not limited to the finite
matrix examples that the runtime executes.
The source separates algebraic, linear, and topological claims. A finite-dimensional matrix com-
putation can exercise a linear identity. It cannot establish the countable Banach-space result or
a generator formula over every division ring. Those claims retain their own source proofs and
dependencies.

Machine execution represents each packet as an ambient vector. It does not construct a basis

makes exact identities easy to compare with the source formulas while retaining the packet index
structure.

1.4 Intertwining and reconstruction

For packet systems P on X and Q on Y , an intertwiner U : X → Y satisfies U T = SU . Resolving

All local equations together are equivalent to the global equation under the packet hypotheses. The
runtime returns the global Boolean, every local residual, and the conjunction of the local Booleans.
It provides the data needed to inspect agreement or failure in a concrete exact case.


1.5 The boundary of finite execution

Countable packet sums require a topology and a convergence condition. Quotient descent requires
invariance. Coordinate transport requires a suitable invertible map. Packet-pure seed counts differ
from unrestricted seed counts because one mixed-support seed can contribute to several source
components. These are mathematical hypotheses, not formatting conventions.
The source records seven explicit boundaries. Their presence is part of the interface. Runtime
action names do not imply that every associated theorem has an implementation, and metadata
listing a boundary does not itself execute that boundary check.


2 Canonical machine representation

2.1 Entrypoint and package identity

The payload is located at source/machine_v1.0.1/. Commands in this volume assume the working
directory is that folder. The entrypoint is PSC_I.machine.json. It points to the record collection,
statement AST, dependency graph, action registry, evidence index, and release files.
The frozen source digest is:
922566ba45640e0d09002ddb119796ec371dd8a37d75a4585aa8b7b16089c9c6


The digest identifies the corrected expanded TeX source. The only mathematical statement changes
from v1.0.0 are explicit nonzero-packet assumptions in the adjoint-closed support-pattern corollary
and the unweighted source-component-count corollary. Both require nonzero packets for their
necessity or counting arguments. All proof bodies are unchanged. The two degenerate examples
are retained in the patch regression. A reformatted PDF or an integrated traditional edition need
not have that digest. Reusing the frozen machine evidence requires retaining its source identity or
recording an explicit crosswalk to a changed source.


2.2 Record identity and source provenance

Each record has a stable ID, kind, title, source section, statement text, optional proof text,
dependencies, semantic annotations, evidence coordinates, and fingerprint. The source locator

includes statement and proof spans and their hashes. These fields make it possible to ask which
statement was encoded and which proof text accompanied it.
There are 28 definitions, 28 theorems, 22 corollaries, 16 propositions, three lemmas, three classical
inputs, seven boundaries, and one remark. The 69 theorem/proposition/corollary/lemma records
have attached proof bodies. Definitions and boundary statements are not counted as proved
theorems merely because they occupy records.
A record fingerprint provides a content identity under the release’s generating convention. It is
not a proof certificate. The release gate checks the source digest, ID count, graph, AST coverage,
selected API behavior, and exact fixtures. It does not establish all mathematical content through
independent formal reconstruction.


2.3 Statement AST and typed signatures

The statement AST has one entry per stable ID. The statuses are 20 TYPED_CORE, 81 STRUCTURED_
SYMBOLIC, and seven TEXTUAL_SEMANTIC. A typed-core record points to a signature declaring
parameters, requirements where supplied, and a return description.
The AST segments statements into prose and mathematical surfaces. Some expressions are
recognized as relations or direct-sum expressions. Others retain latex_expr leaves. Even a typed-
core record can contain these leaves. Consequently, “typed core” refers to the attached interface
signature, not to a complete formal elaboration or a proof term.
The signature for block intertwining describes a logical equivalence between the global and local
equations. Its source proof remains attached separately. The runtime can evaluate a finite instance.
These are three different representations with three different evidentiary roles.


2.4 Dependencies and closure

The recorded graph contains 108 nodes and 97 internal edges. The release gate confirms that the
recorded internal dependencies resolve and that the graph is acyclic. Direct dependencies are stored
on each record. The API can also return a transitive closure.
Closure queries return sorted identifiers. They do not produce a proof order, carry out the proof,
or resolve external classical inputs. A consumer can use the graph to inspect a prerequisite set and
then obtain source statements and evidence for each record.


2.5 Operation profiles and actions

Each record carries source-derived operation metadata, with a transitive profile alongside the direct
profile. The ontology distinguishes structural operations from hypothesis classes. These annotations
support planning and inspection. They should not be interpreted as a verified extraction of every
semantic operation used by an arbitrary proof.
The action registry contains 37 action names associated with 75 records. Eight names are imple-
mented in the runtime. Other entries are marked planner-only or fixture-only. The source has
broader mathematical scope than the executable subset.

3.1 Independent evidence coordinates

The record evidence object separates source, KIR, Python, and Lean. The source coordinate
identifies the authoritative source. The KIR coordinate records the release’s validation status.
Python evidence reports exact finite fixtures for 26 records. Lean evidence points to eight historical
source mappings.
No coordinate upgrades another automatically. Exact arithmetic removes floating-point ambiguity
from a finite computation. It does not quantify over arbitrary fields, modules, dimensions, or topo-
logical spaces. A mapped Lean declaration proves its own formal statement under its dependencies.
Its relation to the source statement must still be read from the mapping.


3.2 Historical Lean linkage

The attached verification tranche records Lean 4.34.0-rc2 and a pinned Mathlib manifest. The
map is dated 2 September 2026. Its eight mappings include definitions, generalized theorems,
one-directional correspondence, and a related sufficient direction. The support-pattern algebra
mapping is explicitly partial. It must not be counted as a full formal certificate for every direction
of the source criterion.
A separate historical report records 35 of 35 obligations for manuscript v1.2.0. The frozen status
marks that lineage as noncanonical for the current expanded source. The historical count and the
eight explicit current-core mappings answer different questions.


3.3 Current reproduction

For this edition, the documented release verifier and exact fixture suite were run from the corrected
payload. Both passed. The verification log is attached in the companion’s build/ directory. All 65
files extracted from the original machine archive retain their original bytes.
An initial invocation used an interpreter without SymPy and failed when the blockification action
imported that dependency. The successful replay used an existing environment containing SymPy.
No runtime action implementation was changed to resolve that environment failure. The two
audited statement corrections were applied separately and have their own provenance record.
No fresh Lean replay is attributed to this companion build. Historical reports remain historical.
If the separate Lean guide performs a fresh replay, it should identify the exact Lean source and
toolchain that were tested rather than rewriting this frozen status file.


3.4 What PASS means

A release-gate pass means the named package checks succeeded. A fixture pass means a concrete
exact computation satisfied its assertion. A transport-gate pass means all operation flags that
this runtime checked were accepted. None of these strings, taken alone, means that the entire
108-record foundation has been formally proved by the runtime.
The full source proof catalog is included so that a reader can inspect mathematical arguments
beyond the runtime. Editorial reproduction of those arguments is not an adversarial proof audit or
a new formal verification claim.

4.1 Input and output conventions

The API is a Python command that emits JSON on successful calls. Exact arithmetic actions
use SymPy matrices. Integers and rational strings such as "3/7" preserve rational values. JSON
floating-point numbers should be avoided when the intended claim is an exact rational identity.
Returned scalar entries are strings.
Payload shapes are conventional rather than comprehensively validated at the API boundary.
Supply nonempty compatible square projector matrices and compatible operators or vectors.
Malformed inputs can raise Python exceptions. The command parser does not present a universal
structured-error contract.
Most computational actions do not call packet validation automatically. Validate the packet family
before interpreting block or analysis output through the theorems. With invalid projectors, a
matrix expression may still be computable while its theorem interpretation fails.

4.3 The two semantic gate actions

CHECK_REALIZATION_PROFILE and TRANSPORT_THEOREM share the same runtime gate. Their pay-
load contains a record ID and a profile. The gate reads that record’s direct action_required_
operations and checks the corresponding profile flags.
The accepted flags are true, VERIFIED, or PRESERVED. False and NOT_PRESERVED produce a negative
list. Other or missing values are unknown. Any negative or unknown required operation blocks the
gate.
This v1.0.1 implementation does not evaluate the profile’s verified_hypotheses, does not use the
transitive operation closure as its required set, and does not execute the returned boundary guards.
It also does not construct a target theorem, a proof object, or an independently verified realization
functor. The preservation flags are caller-supplied declarations.
Thus the action named TRANSPORT_THEOREM is an operation-profile gate. A consumer must sepa-
rately justify target hypotheses, source-to-target interpretation, and any constructions used by the
proof. Unknown flags fail closed only within the operation list actually inspected by the function.

6.2 A countable result is blocked

Using the same profile for the countable unconditional packet theorem returns:
{
    "boundary_guards": [],
    "not_preserved": [
      "completion",
      "topology"
    ],
    "record": "PSC-I-T-COUNTABLE-UNCONDITIONAL-PACKETS",
    "required_operations": [
      "completion",
      "packet_idempotents",
      "topology"
    ],
    "status": "BLOCKED",
    "unknown": []
}


The profile does not preserve the topological and completion operations required by this gate. A
finite linear profile therefore cannot be used to pass this countable request.
The source theorem additionally requires a real or complex Banach space, unconditional reconstruc-
tion, and a uniform multiplier bound. These hypotheses remain visible in its statement. Supplying
permissive operation flags would not prove those hypotheses. The richer source contract and the
narrower executable gate must be kept distinct.


6.3 Changing a profile without changing evidence

A profile file is a declaration supplied to the runtime. Editing its flags changes the gate’s output. It
does not create mathematical preservation evidence. A downstream system that wants a transport
certificate must retain the arguments or formal certificates justifying those flags and the target
hypotheses.
The correct use is sequential: identify the exact record, inspect its source and dependency context,
establish a target realization, justify the relevant preservation properties and hypotheses, then use
the gate as an explicit consistency check. Its output can be attached to the resulting evidence
record as one component.

103. Equational realization principle

Stable ID. PSC-I-T-REALIZATION-EXPORT
Kind and regime. theorem; algebraic, linear, topological
Statement.

proof additionally uses a chosen biproduct, kernel, cokernel, quotient, tensor product, or completion

transported to D.

Attached source proof. Functoriality gives

a. A structural induction on the construction of a morphism expression therefore carries every
